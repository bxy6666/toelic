# TOEIC Practice Studio 两人演讲稿

建议总时长：10-15 分钟  
分工建议：讲者 A 负责第 1-9 页，讲者 B 负责第 10-19 页。  
讲述方式：不要逐字背诵，可以按本稿的逻辑自然表达。

## 讲者 A：项目背景、开发方法与架构边界

### 第 1 页：开场

各位老师、同学大家好。我们今天汇报的项目是 TOEIC Practice Studio，也就是一个 AI 驱动的托业练习工作室。

这个项目不是单纯做几个网页页面，而是一次从需求建模、设计、实现到验收的完整软件工程实践。它的核心目标，是做出一套本地个人版的学习闭环：用户可以生成题目、完成听力和语法练习、沉淀错题，再通过学习统计看到自己的薄弱点。

从软件基础实验的角度看，我们希望展示的不只是“功能能跑”，还包括需求如何被约束，过程如何被控制，对象如何被抽象，以及最后如何通过验收记录证明项目确实完成。

### 第 2 页：汇报路线

今天我们会按四条线来讲这个项目。

第一条是开发流程，也就是 spec-driven coding 如何把一个比较模糊的想法，逐步变成可审阅、可执行、可验收的任务。

第二条是技术路线，我们会说明 Next.js、本地 API、SQLite 和华为云 MaaS 之间的边界如何划分。

第三条是功能成果，重点展示听力、语法、错题和统计如何形成学习闭环。

第四条是验收和反思，通过 acceptance 记录说明项目如何从“可用”进一步走向“可靠”。

### 第 3 页：学习痛点

这个项目的出发点来自一个比较常见的学习问题：题做了很多，但反馈链路经常断开。

比如听力练习里，如果答题前就能看到英文选项，训练就会不够接近真实考试；同时播放、作答和解析如果分散在不同工具里，学习体验也会被割裂。

语法练习也类似，很多题源分散，解析质量不稳定，中文学习者很难把题目和具体语法点对应起来。

再往后，错题如果只是停留在一次错误记录，而没有掌握状态、重复错误次数和重新练习入口，那么下一次复习就很难精准。统计也是一样，只知道做了多少题，并不能告诉用户薄弱点在哪里。

所以我们不是为了做一个 AI 题目玩具，而是想补上从生成、练习、复盘到反馈的完整闭环。

### 第 4 页：产品目标

因此，这个项目被定位为本地个人版 TOEIC 学习闭环。

这里有一个重要取舍：第一版不做登录、多端同步、云部署、班级管理这些复杂功能，而是先保证一个人在本机上可以完整使用。

整个闭环可以概括为四步：第一步，用 AI 生成原创托业风格题目；第二步，用户完成听力或语法练习；第三步，错误题目进入错题本，可以复练和标记掌握；第四步，学习统计根据记录生成趋势和薄弱点反馈。

题目生成只是入口，真正让学习持续下去的，是后面的记录、错题和统计。

### 第 5 页：用户流程与需求模型

这一页把产品主流程抽象成一个需求模型。

参与者主要有两个：一个是学习者，另一个是外部 MaaS 服务。本地系统边界是 TOEIC Practice Studio，系统内部负责生成请求、练习交互、解析展示、错题管理和统计计算。

这里特别把 MaaS 标成外部服务，是为了避免混淆“外部 AI 能力”和“本项目自身负责的业务功能”。MaaS 负责生成候选题目，但是否可以进入数据库、是否符合题型结构、是否能展示给用户，都由本地后端来判断。

所以这页的重点不是画图本身，而是说明我们从学习者目标出发，抽取出了系统必须提供的能力，并且划清了应用内部和外部服务之间的边界。

### 第 6 页：开发方法

在开发方法上，我们采用了 spec-driven coding。

它的核心思想是：先让需求可审阅，再让实现可验收。也就是说，不是一开始就直接写页面，而是先把范围、数据、接口、安全和验收标准写清楚。

项目中一共有五个闸门：Gate 1 是 `spec.md`，负责明确规格；Gate 2 是 `design.md`，把规格转换成设计；Gate 3 是 `tasks.md`，拆成可执行任务；Gate 4 才进入实现；Gate 5 则由 `acceptance.md` 记录验收结果。

这样做的好处是，每次修改都有来源，每个功能都有出口条件，最后也能留下证据，而不是只靠口头说明“我做完了”。

### 第 7 页：四份文档链路

这一页展示的是项目的文档链路。

`spec.md` 先限定范围，明确要做什么、不做什么。比如第一版包含听力、语法、错题、统计和设置，但不包含登录、多端同步、云部署和支付。

`design.md` 再把规格转换成可实现方案，包括页面结构、API 设计、数据模型和安全边界。

`tasks.md` 把设计拆成 T01 到 T22 的小步任务，方便逐项推进。

最后 `acceptance.md` 记录每项任务的 PASS / FAIL、验证方式和备注。这样从规格到设计、从任务到验收，就形成了一条可复盘的证据链。

### 第 8 页：推进证据

这里可以看到，项目从 T01 到 T22 已经全部完成。

T01 到 T04 是项目骨架，包括 Next.js、Tailwind、shadcn/ui、Prisma、SQLite 和基础页面。

T05 到 T08 是核心后端，包括设置、MaaS Client、题目生成和答题记录。

T09 到 T12 是练习闭环，包括听力、语法、错题本和学习统计。

T13 到 T15 是安全检查和最终验收。

后面的 T16 到 T22 是体验增强，比如 Motion 动效、进度条、错题重新练习、首页计划卡片和统计页卡通仪表盘。

这些任务不是只写在计划里，而是在验收文档里都有对应验证记录，比如 lint、build、Prisma、浏览器 smoke 和真实 MaaS 生成。

### 第 9 页：技术架构

技术架构上，项目使用 Next.js App Router 作为前端和本地 API 的统一框架。

前端页面负责学习体验，包括首页、听力、语法、错题、统计和设置。浏览器端不会直接持有 MaaS API Key，也不会直接访问华为云 MaaS。

后端 API Route 负责请求校验、读取服务端环境变量、调用 MaaS、解析结果、校验题目结构，并把合法数据写入 SQLite。

数据库层使用 Prisma + SQLite，保存四类核心数据：题目、练习记录、错题状态和用户设置。

这种架构适合课堂演示，也能保证一个重要安全边界：API Key 留在服务端，前端只请求本地接口。

接下来由第二位同学继续介绍数据模型、核心功能、验收结果和项目反思。

## 讲者 B：数据模型、功能成果、验收与反思

### 第 10 页：数据模型

我接着介绍项目的数据模型。

这个项目用四张表支撑完整学习闭环。

第一张是 `Question`，用于保存 AI 生成的题目，包括题干、选项、答案、中文解析、标签，以及听力题需要的 `listeningScript` 或语法题需要的 `grammarPoint`。

第二张是 `PracticeRecord`，用于保存每一次作答行为，包括用户答案、是否正确和作答时间。

第三张是 `Mistake`，也就是错题状态表。它不会简单重复存错题，而是记录同一道题的错误次数、最后错误时间，以及 `new`、`reviewing`、`mastered`、`removed` 等状态。

第四张是 `UserSetting`，保存本地学习偏好，比如默认难度、题量和听力语速。需要注意的是，API Key 不会保存到数据库里。

这个模型没有做得过度复杂，但足够支撑生成、练习、错题和统计四个核心能力。

### 第 11 页：AI 生成链路

AI 生成链路是项目里比较重要的一部分。

我们的设计原则是：模型输出不能直接进入业务。

用户在前端选择练习类型、题型、难度和题量后，请求会发送到本地 API Route。服务端读取 MaaS 配置，再通过 MaaS Client 调用 DeepSeek-V3.2 生成题目。

但是生成结果不会立刻落库，而是先经过 JSON 解析和字段校验。比如听力题必须包含 `listeningScript`，语法题必须包含 `grammarPoint`，每道题只能有一个正确答案，并且答案必须存在于 A/B/C/D 选项中。

如果模型返回非 JSON、字段缺失或答案结构不合法，后端会拒绝写入数据库。这样能避免把不稳定的 AI 输出直接变成业务数据。

### 第 12 页：听力练习

听力练习页最能体现学习规则。

在用户提交答案之前，页面只显示 A/B/C/D，不提前展示英文选项正文。这样可以避免用户通过阅读选项来猜题，更接近真实听力考试。

播放部分使用浏览器 Web Speech API，朗读听力脚本和选项内容。用户听完之后选择答案，提交后才会看到完整选项、正确答案、自己的答案和中文解析。

这个设计看起来是一个小交互，但它实际上对应了 `spec.md` 里明确写下的硬性规则，也通过后续浏览器验收进行了检查。

### 第 13 页：语法练习

语法练习和听力练习复用了同一个练习工作区，但交互规则不同。

语法题答题前可以直接显示题干和选项。用户选择答案并提交后，页面会展示正确答案、中文解析和对应语法点。

这里的重点是：题目不是一次性消费品。用户答过的题会进入练习记录，答错的题会进入错题链路，统计页也会基于这些记录计算正确率和薄弱点。

所以语法练习不是一个孤立页面，而是整个学习闭环的一部分。

### 第 14 页：错题本

错题本的作用，是让每一次错误都变成下一次练习的入口。

当用户答错时，系统会自动创建或更新错题记录。同一道题重复答错时，不会创建重复记录，而是增加 `wrongCount`，并把状态更新为 `reviewing`。

错题本里还提供重新练习、标记掌握和移除功能。`new` 表示首次答错，`reviewing` 表示重复答错，需要优先复习，`mastered` 表示已经掌握，`removed` 则是软移除。

这样错题本就不只是一个静态列表，而是一个动态复盘系统。

### 第 15 页：学习统计

学习统计页把练习结果转化成可行动反馈。

它会展示今日练习、总练习量、总正确率、听力正确率、语法正确率、当前错题数、已掌握错题数、最近 7 天趋势，以及高频薄弱标签。

这些数据来自 `PracticeRecord` 和 `Mistake`，不是固定占位数据。也就是说，用户完成练习之后，统计会跟着变化。

V1.7 又把统计页优化成了比较适合课堂展示的轻卡通仪表盘，加入了趋势图、数据卡片和薄弱标签层级，让用户更容易判断下一步该练哪里。

### 第 16 页：UI 迭代

这个项目的 UI 也经历了多轮迭代。

V1.1 先完成真实统计和练习工作区打磨；V1.2 引入 Motion 动效、动态背景和卡通贴纸；V1.3 增加生成中状态、进度条和完成面板；V1.4 处理指标卡片对齐和响应式巡检；V1.5 补齐错题重新练习闭环；V1.6 优化首页 Hero 和今日计划卡片；V1.7 重构统计页仪表盘。

这里想强调的是，UI 迭代不是单纯为了装饰，而是为了提升可读性、反馈感和课堂演示稳定性。

### 第 17 页：验收结果

最后看验收结果。

项目不是只验证“页面能打开”，而是从功能、工程和安全三个层面做了记录。

工程层面，`npm run lint` 通过，`npm run build` 通过，Prisma 迁移和浏览器 smoke 都有记录。

功能层面，听力和语法都完成了真实 MaaS 题目生成，并写入 SQLite；错题、统计和重新练习也都有对应验证。

安全层面，API Key 不进入前端，不使用 `NEXT_PUBLIC` 暴露敏感变量，设置页只返回 `hasApiKey` 这类状态，不回显完整密钥。

所以 `acceptance.md` 的价值，就是把“我觉得完成了”变成“证据显示通过”。

### 第 18 页：总结反思

总结来看，这个项目最大的收获有四点。

第一是方法收获。先写规格，再做设计和任务拆解，可以把模糊想法变成可审阅、可执行、可验收的开发链路。

第二是建模收获。用例图、类图和时序图分别帮助我们解释需求边界、静态结构和对象交互，不只是展示页面截图。

第三是工程收获。AI 生成结果不能直接进入业务，必须经过服务端边界、JSON 解析、字段校验和数据库落库检查。

第四是产品收获。学习工具的价值不只在生成题目，更在作答记录、错题复练和统计反馈形成持续学习闭环。

当然，当前项目仍是本地个人版，还没有账号体系、班级管理、多端同步和更丰富的题型数据。后续如果扩展，也应该继续按 spec-driven 流程推进，先定义规格，再补设计、任务、验收和实现。

### 补充：spec-driven 开发总结、收获与个人体会

这里我想再补充一下对 spec-driven 开发方式的总结和个人体会。

在做这个项目之前，我对开发流程的理解更多是“先想到功能，再尽快把页面做出来”。但在这个项目里，我们先写 `spec.md`，再写 `design.md`，然后拆 `tasks.md`，最后用 `acceptance.md` 做验收记录。这个过程让我明显感受到，规格文档不是额外负担，而是在帮开发减少不确定性。

第一个收获是边界意识更强了。比如第一版明确不做登录、多端同步、云部署和班级管理，这让项目没有因为“顺手加功能”而失控。很多时候不是功能越多越好，而是先把一个最小闭环做完整。

第二个收获是任务拆分更清楚了。T01 到 T22 不是随便列清单，而是从项目骨架、数据模型、后端 API、练习闭环，再到 UI 和验收逐步推进。这样做的时候，每一步都知道当前目标是什么，也知道暂时不该做什么。

第三个收获是验收意识更强了。以前可能页面能打开就觉得完成了，但这次我们会记录 lint、build、Prisma、浏览器 smoke、MaaS 真实生成和安全边界检查。也就是说，完成不再只是主观感觉，而是可以被别人复查的证据。

第四个体会是，spec-driven 特别适合和 AI 辅助开发结合。AI 可以帮助生成代码、补全文档、整理结构，但如果没有规格约束，它也很容易把范围扩大，或者生成看起来合理但不符合项目边界的内容。`spec.md` 和 `design.md` 就像给 AI 和开发者共同设定的一套轨道，让每次修改都有依据。

对我个人来说，这次最大的变化是从“实现功能”的思维，转向“控制项目”的思维。一个软件项目不只是把页面和接口写出来，还要能解释为什么这样设计、如何保证安全、如何验证结果，以及后续如何继续扩展。

所以我对 spec-driven 开发的最终理解是：它不是让开发变慢，而是把前期想清楚、过程拆清楚、结果验清楚。尤其在课程项目里，它能让我们的汇报不只是展示成品，而是展示一个项目从想法到系统的完整成长过程。

### 第 19 页：结束

以上就是我们对 TOEIC Practice Studio 的项目汇报。

最后用一句话总结：这个项目让我们理解到，软件开发不是把页面堆出来，而是把需求、模型、代码和验收连成一个可解释、可复盘的系统。
